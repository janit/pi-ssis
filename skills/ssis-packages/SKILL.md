# Working with SSIS packages

Use the `ssis_*` tools. Do not read `.dtsx` files with a file reader or change them with a text edit tool: the XML is very large, and hand edits break the ids and references the designer depends on.

## Reading

1. `ssis_overview` on the project directory (or `.ispac`) to see the packages, project connections and project parameters.
2. `ssis_package` on one package for its control flow in execution order. `detail: "full"` adds complete SQL and script source; ask for it only when you need the code.
3. `ssis_dataflow` for what happens inside a data flow task: sources, transformations, column expressions, destination mappings.
4. `ssis_search` to answer "where is X used" across every package. Search for the table, column, variable (`User::Name`), parameter (`$Package::Name`, `$Project::Name`) or any text.

How to read the output:

- Tasks are listed in execution order. `after: A (Success)` is a precedence constraint; `(Failure)` and `(Completion)` are the other outcomes, and `and <expr>` / `or <expr>` / `when <expr>` add an expression. Several constraints joined with `OR` mean any one is enough.
- Address a task by its name, or by refId when names repeat: `Package\Container\Task`.
- `expression Prop = ...` means the property is computed at run time and overrides the stored value. A connection with a `ConnectionString` expression does not use the connection string shown.
- A variable shown with `expression:` is recomputed every time it is read.
- `sql (from Variable)` means the statement text lives in that variable, not in the task.
- In SQL, `?` markers are positional parameters; the `parameters:` line maps them to variables in order.
- Values shown as `<sensitive>` or `<encrypted>` are not stored readably. Do not guess them.

When explaining a package, describe the business outcome first (what is loaded from where to where), then the control flow, then anything risky: disabled tasks, failure paths, scripts, dynamic SQL, hard-coded paths and servers.

## Editing

Use `ssis_edit`. It applies your operations in order, validates the result, and writes the file only if the package is still structurally sound. Only the affected lines change, so the diff stays reviewable.

- Read the package first so targets match existing names.
- Batch related operations in one call; if any fails, nothing is written.
- Use `dryRun: true` when unsure whether an edit is accepted.
- After editing, re-read the affected task with `ssis_package` and tell the user what changed.
- Relay every `Note:` in the result. They flag things you cannot fix from here, such as stale column metadata after changing a source query, or a task that still expects a result set.
- `rename_variable` and `rename_parameter` update references inside the package. They do not update parent packages, SSISDB environment references, or script code that uses a bare variable name. Run `ssis_search` across the project for the old name afterwards.
- `ssis_validate` checks structure only. Never tell the user a package "works" on that basis; say it is structurally valid and still needs a run in Visual Studio or a test catalog.

Limits to state plainly rather than work around:

- Adding or removing data flow components, or changing their columns, needs Visual Studio: the column and lineage metadata is generated by the designer against a live database.
- Legacy packages (format below 6, SSIS 2005/2008) are read-only. They must be upgraded in Visual Studio first.
- Packages saved with `EncryptAllWithPassword` or `EncryptAllWithUserKey` cannot be read at all.
- Sensitive parameter values cannot be written; they are set at deployment or in an SSISDB environment.

## SSIS expression language reminders

It is not T-SQL or C#. Strings use double quotes, `+` concatenates, `==` compares, `&&`/`||` are logical operators, casts are written `(DT_WSTR, 50) @[User::Id]`, and the conditional is `cond ? a : b`. Variables are referenced as `@[User::Name]`. Backslashes in string literals are escaped: `"C:\\Import"`.
